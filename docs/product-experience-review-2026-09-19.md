# Consumer / Provider 产品体验复评 — 2026-09-19

结论：当前可以作为有运营支持的开发者受控测试网；不宜宣称普通用户可自助使用、Provider 可无人值守持续接单。底层身份、支付、回执与批量结算已有实证，最大产品缺口是统一入口、预算生命周期、真实流式和任务质量验收。

本次是评估，不变更线上代码、预算、授权或合约，也没有新增付费模型请求。

## Consumer：安全基础已有，首次价值路径太长

已有优点：无需 Docker；正常调用不必每次弹钱包；正文与回执签名校验；未知执行结果不自动重放；幂等请求持久化；预算、待结算、托管、释放等状态已区分；无钱包提示较前改善。

当前流程仍是：安装 → 钱包签名 → 链上访问授权 → 准备 gas 和测试币 → 充值 → 运营开预算且 Provider 激活 → 复制 API 配置 → 外部客户端发题。UI 没有承接用户的第一个实际任务。

| 问题 | 证据 | 产品改进 |
|---|---|---|
| 默认入口仍与受控 V10 分裂 | `consumer-runtime.mjs:110,660` 无显式配置回到 V8；`consumer.mjs:250` 默认模型 5.5；V10 tgz 尚未发布 npm | 统一受控测试网安装入口、签名清单、模型目录和说明。旧入口明确升级，版本不能静默混用 |
| 首页是 API 管理台，没有题目输入、模型选择、结果预览 | `consumer-runtime.mjs:2648–2652` 四页为概览/钱包/记录/分享；旧 Web Playground 使用旧 ABI | 增加一个最小试用页，默认展示可用模型、预计价格和预算。开发者仍可直接复制 API 配置 |
| 预算仍需运营人工开通 | `consumer-runtime.mjs:2672`；本轮 `/ready` 的 503 | 在受控准入内自动化申请、确认、Provider 预激活、续期与到期释放；失败有持续状态和恢复动作 |
| 用户会把执行额度误解为实际消费余额 | `reserved_execution.py:254`；`MycoSettlementV10.sol:716–731` | 分开展示实际消费、剩余执行额度、暂锁金额和释放时间；在发出请求前展示 MAX 与报价 |
| “待核实”会长期停留，缺少自助恢复入口 | `consumer-runtime.mjs:2046,2683` | 请求详情展示请求 ID、是否派单、是否执行、是否收费、恢复进度；加入可验证的未执行凭据和已完成结果取回 |
| 长操作仍全局禁用按钮，普通错误 3.2 秒消失 | `consumer-runtime.mjs:2659–2661` | 保留导航和只读操作；显示持久任务进度与交易链接；不确定交易先查回，不能简单重复发送 |

建议首屏主任务是“开始试用”，随后自然过渡到 API 接入。试用预算可由受控运营方赞助，需明确额度、资金控制方和有效期；不能用自动化替用户暗中扩大授权。

多钱包选择可使用 [EIP-6963](https://eips.ethereum.org/EIPS/eip-6963)，无钱包时展示可执行的安装/打开浏览器/重新检测路径。移动布局通过不等于手机钱包登录已经通过。

## Provider：可以运维，尚不能自助持续经营

当前实际步骤包括依赖与镜像、收款地址、授权与质押、模型账户登录、受控准入、预算通道预激活、联网接单、释放与领取收益。浏览器、终端、钱包和登录页反复切换。

最先解决以下问题：

1. **版本一致性。** `provider.mjs:9–12` 仍固定 0.1.37 旧镜像；`install-provider.sh:20` 默认 V8；`operator_setup.py:1082` 只接受协议 2–9，没有 V10 向导。现有 V10 节点来自专用运维部署。
2. **提现封装遗漏。** `Makefile:443–446` 只拦截 8/9，10 会落入旧 `v4-claim-payout` 路径。应先对不支持版本拒绝执行，再提供正确的 V10 外部收益钱包流程。本轮未执行该命令，不能推断已经发生损失。
3. **预算激活与续期不能依赖 SSH。** 当前需要六次确认，并在通道开始至少 300 秒前预激活；新增通道仍要求停止/激活/重启（`docs/v10-provider-execution-journal.md:25–39`）。应做可恢复的持久状态机和经过安全设计的在线激活；不能缩短确认或伪造空账本绕过约束。
4. **同一控制台完成日常运营。** 显示登录是否有效、实际可用模型、准入状态、可接单额度、执行中任务、收益阶段、gas 与备份健康。只有全部业务条件满足才显示可接单。保留“暂停接单→排空→升级→恢复”入口。
5. **收益需要由用户自己完成闭环。** 运维脚本证明到账，不代表 Provider 知道如何领取。看板区分待上链、争议期、可领取、已到账，并让本人钱包确认领取交易。

建议主流程固定为“准备环境 → 连接账户与资金 → 开始接单”，每个阶段只突出一个下一步；后台保存详细步骤，关闭页面或重启后可继续。链上不可避免的等待应有明确倒计时和完成通知。

## 效果与速度：不要把传输成功当任务成功

以下耗时来自原始验收文件，不是本轮重新发出的调用。

| 样本 | 结果 | 可证明什么 |
|---|---|---|
| R1 修复后短请求 48 次 | 48/48；P50 9.981 秒，P95 15.645 秒 | 这组修复后测试稳定；每次输出只有 5 tokens，混合 5.5/Sol |
| R3 前 99 次短请求 | 99/99；P50 13.862 秒，P95 17.857 秒；第 100 次另记 14.723 秒 | 单条线路顺序短请求可用；不能当并发吞吐或长期成功率 |
| V10 Sol 糖果题 | 52.087 秒，1666 output tokens，答案 21 并有证明 | 单个数学样本正确；不是通用智力评估，不能与不同提示的旧 27.3 秒直接比较 |
| V10 Sol HTML | 32.701 秒，1129 output tokens，2926 字节，签名摘要匹配 | 确由网络交付代码；视觉质量验收未通过 |

HTML 本轮浏览器实测：车轮/曲柄在画面上方，脱离车架；暂停按钮可以切换并暂停动画，但脚没有跟随踏板。源码将 `translate(...)` 和 CSS rotate 动画施加在同一个 SVG 元素上，导致定位被动画覆盖。不能用有签名、有文件、HTTP 200 证明“鹈鹕骑车动画完成”。

应建立按任务类型的交付检查：生成 → 沙箱预览/运行 → 规则与视觉检查 → 用户事先同意的次数及费用上限内修复 → 交付。HTML 检查脚本错误、关键元素布局、动画和控件；数学题检查题意、答案与推理；数据任务检查格式和数值。签名保证来源/完整性，质量检验验证任务结果，两者分别记录。

当前 SSE 是缓冲式：`consumer-runtime.mjs:2366` 等整个请求完成，`:2381` 再生成事件；`codex_app_backend.py:233` 表明后端不支持真实流式。用户首个可见答案基本要等整段完成，因此“只回答 OK 也等 10–18 秒”的体感明显偏慢。

优化顺序：

1. 分段记录 Consumer 预检、Relay 预检、排队、模型启动、模型首 token、生成、证明、返回耗时。当前总耗时不能定位主要瓶颈，不应直接归咎链上或模型。
2. UI 立即确认已接收，展示真实阶段；贯通后端到 Consumer 的增量输出，再测真正 TTFT。SSE 格式本身不代表流式生成，参照 [MDN SSE](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)。
3. 设计分块证明或明确标记未最终核验的增量输出，最终内容绑定签名回执；断连按同一请求取回，不重复计费。
4. 基于分段数据优化重复读链和连接/会话建立。缓存必须绑定规范区块、通道和时间有效性，不降低安全验证来制造低延迟。
5. 用相同模型、提示、上下文、推理强度、输出预算做直连与网络对照，才能量化 MycoMesh 自身的开销。先从单槽到满槽，再过载测排队和拒绝；目前没有可据以宣传的并发容量或 tokens/s 基准。

## Web3 经济与可靠性

两个 Relay 各 100 笔的阈值验收原始文件已复核，都由 count 触发并分成 32/32/32/4。合计 200 条变成 8 笔交易是明确进展；但每条回执仍平均约 42.3 万 Gas，主要问题不会靠继续扩大 batch size 消失。

R1 的 100 笔实际费 0.320684 TestUSDC，Gas 42,404,161；R3 为 0.214220 TestUSDC，Gas 42,225,025。这里仅确认托管；相应验收文件 `payout_verified=false`，不能说这两批已经全部领取。其他历史领取有独立到账证据。

每次 MAX=0.1 的 100 笔消耗 10 TestUSDC 执行容量，而实际费用只有该容量的约 3.21% / 2.14%。**不是多收 31–47 倍费用，而是可继续执行的额度按最坏值消耗，差额不能立即在该通道重复使用。** 这会造成“花得很少却不能用了”的直观困惑。

先做准确输入报价和可执行的输出预算，降低不必要预留；若要回收已完成请求的差额，必须重新设计并证明跨 Relay、重启和未提交回执场景下的资金约束。不能简单本地加回余额。进一步测量存储/签名校验成本，评估压缩记账、累计结算或更低成本结算环境，同时保留争议证据；这属于合约版本设计，不是前端补丁。

可靠性已有在线 Provider 独立提交、不重复结算的证据。但 Relay 真正离线的故障演练仍未完成，过去两次是前置保护中止，不能算通过。还需要长时间运行、通道自动续期、RPC 故障、重启、网络分区的业务验收。Sol 仍单路径；三个 Bridge 不能抵消模型供应单点。

文档还应清楚说明当前受控准入、测试委员会和正文可见范围。旧 `provider-runtime-and-client-delivery.md` 的 V6 与端到端隐私描述不能直接套用当前 V10 请求路径。

## 建议执行顺序与验收标准

以下是建议目标，不是现有成绩或工期承诺。

| 顺序 | 交付 | 如何证明完成 |
|---|---|---|
| P0 | 一套当前协议的安装、清单、文档与提现入口 | 全新机器按公开说明进入正确网络；不支持版本明确拒绝，绝不回落旧提现流程 |
| P0 | 自动预算确认、预激活、续期与状态恢复 | 连续跨越至少两个真实通道周期，不需 SSH、不丢账本、不重复锁款；关闭浏览器后仍继续 |
| P0 | Consumer 首单向导与错误恢复 | 新用户不读开发文档完成试题；待核实请求可看到进度并取回结果；没有静默重跑 |
| P1 | 真流式与分段性能指标 | 预设短任务 TTFT 目标 P50≤3 秒/P95≤8 秒，再按模型校准；分别报告未达标原因，不用进度文字冒充首 token |
| P1 | Provider 常驻控制台与领取收益 | 用户独立接单、暂停、恢复并用本人钱包完成一次到账；主动操作目标不超过 5 分钟，下载与链上等待单独计时 |
| P1 | 按任务检查产物并有限修复 | 固定小型题集含数学/代码/HTML，检查可运行和需求满足；这份车轮错位产物必须被检出 |
| P1 | 独立 Sol 备用路径与离线恢复 | 真实停机演练后结果可追回，费用只结算一次；不能在未知执行状态下换路重跑 |
| P2 | 合约成本与额度利用率 | 同样工作负载报告每请求 Gas、实际费用、MAX 利用率、锁定时长，再决定设计变更 |

建议核心产品指标是“无需运营介入的任务完成率”，分别统计首单转化、7 日回访可用率、任务质量通过率、TTFT、未知状态恢复时间、Provider 接单在线率与收益到账时间。HTTP 200、容器运行和单元测试数量都不能替代这些指标。
